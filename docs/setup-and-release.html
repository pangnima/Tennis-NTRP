누구를 위한 문서인가: 프론트엔드는 해 봤지만 배포는 처음인 사람. 위에서부터 순서대로 따라 하면 된다. 기준 시점: 2026-11-27. 대시보드(Vercel·Supabase·Google)의 메뉴 이름은 가끔 바뀐다 — 이름이 다르면 같은 뜻의 메뉴를 찾으면 된다. 보기 좋은 HTML판: 같은 폴더의 setup-and-release.html을 더블클릭하면 브라우저에서 열린다(목차·코드 복사 버튼). 이 md가 정본이고, md를 고친 뒤 node scripts/docs-to-html.mjs docs/setup-and-release.md docs/setup-and-release.html로 다시 만든다. 비밀값은 이 문서에 없다. 「어디서 찾는지」만 적는다. 이 문서는 GitHub에 올라가므로 여기에 키·비밀번호를 적지 않는다.

각 단계는 같은 모양이다.

  • 왜 — 이 단계가 하는 일 한 줄
  • 할 일 — 번호 순서. 회색 상자의 명령은 그대로 복사해 붙여 넣는다
  • 확인 — 성공하면 무엇이 보이는가
  • 막히면 — §8 문제 해결에서 증상을 찾는다

명령 상자는 운영체제별로 나뉜다. Windows는 PowerShell(시작 메뉴 → 「PowerShell」), Mac은 터미널(Spotlight → 「터미널」)에 붙여 넣는다.

#코드가 사용자에게 닿기까지

 ┌──────────── 내 PC ─────────────┐
 │  코드 고치기 → npm run dev      │   localhost:3000 은 언제나 테스트 DB(dev)에 붙는다
 └──────────────┬─────────────────┘
                │ git push
                ▼
 ┌──── GitHub (pangnima/Tennis-NTRP) ─────────────┐
 │  dev 브랜치  ── 평소 작업이 쌓이는 곳            │
 │  main 브랜치 ── 실서비스에 나간 코드 (릴리스 때만) │
 └───────┬──────────────────────────┬────────────┘
         │ dev에 push하면 자동         │ main에 push하면 자동
         ▼                           ▼
 ┌─ Vercel Preview ─────┐   ┌─ Vercel Production ───────────────┐
 │ 미리보기 주소(매번 다름) │   │ https://baselineplay.vercel.app   │
 │ → Supabase dev 에 붙음 │   │ → Supabase prod 에 붙음 (실사용자) │
 └──────────────────────┘   └───────────────────────────────────┘

 Supabase dev  (Tennis-NTRP-dev, xiwwbgltkbvxdzxxxoba)        — 테스트 계정 57명, 마음대로 써도 된다
 Supabase prod (Tennis-NTRP-prod, rjuhydxaoizgfiatyfpo) — 실사용자. 데이터를 손으로 고치지 않는다
 Google Cloud  — 「Google로 계속하기」 로그인 버튼의 설정

핵심 세 가지

  1. 평소에는 dev 브랜치에서만 일한다. dev에 push하면 미리보기가 만들어질 뿐, 사용자는 아무 영향을 받지 않는다.
  2. 실서비스 배포 = dev를 main에 합치고 push하는 것. 그러면 Vercel이 알아서 빌드해 baselineplay.vercel.app을 바꾼다.
  3. DB는 둘이다. 내 PC와 미리보기는 dev DB, 실서비스만 prod DB를 쓴다. DB 구조를 바꿀 때는 dev에 먼저, 실서비스 배포 때 prod에 같은 것을 적용한다.

#1. 계정과 로그인

왜 — 개발·배포에 관여하는 서비스는 다섯 곳이다. 새 PC에서는 브라우저로 각각 로그인만 하면 된다.

서비스 주소 여기서 하는 일 자주 가는 화면
GitHub github.com 코드 보관. 저장소 pangnima/Tennis-NTRP 저장소 → Branches · Pull requests
Vercel vercel.com 코드를 빌드해 인터넷에 올린다. 프로젝트 baselineplay 프로젝트 → Deployments · Settings → Environment Variables
Supabase supabase.com/dashboard DB·로그인 서버. 프로젝트 둘(dev·prod) 프로젝트 → Table Editor · SQL Editor · Authentication · Project Settings
Google Cloud Console console.cloud.google.com 「Google로 계속하기」 버튼의 OAuth 설정 APIs & Services → Credentials · OAuth consent screen
Claude claude.ai Claude Code 로그인 —

할 일

  1. 다섯 곳 모두 어떤 방법으로 가입했는지(이메일·GitHub로 로그인·Google로 로그인) 비밀번호 관리자나 개인 메모에 적어 둔다. Vercel·Supabase는 보통 「GitHub로 로그인」이다.
  2. GitHub·Vercel·Supabase에는 2단계 인증(Two-factor)을 켜 둔다. 이 계정을 잃으면 서비스를 통째로 잃는다.

확인 — 다섯 곳에 로그인했을 때 Vercel에 baselineplay, Supabase에 프로젝트 두 개가 보인다.

#2. 비밀값 지도

왜 — 앱은 「어느 DB에 붙을지」와 「어떤 열쇠를 쓸지」를 환경변수로 받는다. 같은 이름의 변수에 환경마다 다른 값을 넣는 것이 전부다.

#가장 중요한 규칙 — 이름의 NEXT_PUBLIC_

이름 모양 뜻 이 프로젝트에서
NEXT_PUBLIC_… 공개해도 되는 값에 붙이는 이름표. 브라우저(사용자 PC)까지 전달된다. 빌드할 때 코드 안에 박힌다 NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, NEXT_PUBLIC_SITE_URL — 꼭 있어야 한다
그 외 서버에서만 읽는 값 SUPABASE_SERVICE_ROLE_KEY — 유일한 진짜 비밀. 절대 NEXT_PUBLIC_을 붙이지 않는다

⚠ 실제로 있었던 사고(2026-11-27) — 「NEXT_PUBLIC_은 넣으면 안 된다」고 잘못 이해해 Vercel에서 NEXT_PUBLIC_SUPABASE_URL·_ANON_KEY를 지웠더니 실서비스의 모든 페이지가 500이 됐다(MIDDLEWARE_INVOCATION_FAILED). 올바른 규칙은 「비밀값에 NEXT_PUBLIC_을 붙이지 않는다」이다. 공개 값은 NEXT_PUBLIC_이 맞다.

#값마다 — 무엇 · 어디서 · 어디에

변수 무엇 어디서 찾나 (Supabase 대시보드, 해당 프로젝트) 넣는 곳 비밀?
NEXT_PUBLIC_SUPABASE_URL DB·로그인 서버 주소 프로젝트 화면 위쪽 [Connect] 버튼, 또는 Project Settings → Data API의 Project URL. 모양: https://<프로젝트ID>.supabase.co 로컬 = dev · Vercel Preview = dev · Vercel Production = prod 공개
NEXT_PUBLIC_SUPABASE_ANON_KEY 브라우저가 쓰는 공개 키(권한은 DB의 RLS가 막는다) Project Settings → API Keys → 「Publishable and secret API keys」 탭의 Publishable key(sb_publishable_…). 옛 「Legacy API Keys」 탭의 anon(eyJ…)도 동작한다 위와 같음 공개
SUPABASE_SERVICE_ROLE_KEY 서버 전용 만능 열쇠. 게임을 기록할 때 레이팅을 다시 계산한다. 없으면 랭킹·레이팅이 멈춘다 Project Settings → API Keys → 「Legacy API Keys」 탭의 service_roleReveal — 또는 같은 화면 「Secret keys」의 sb_secret_…(Legacy가 폐지되면 이쪽으로 바꾼다, Supabase 예고는 2026년 말·미확정) 위와 같음 비밀
NEXT_PUBLIC_SITE_URL 링크 미리보기(OG)·로그인 복귀에 쓰는 사이트 주소 값은 https://baselineplay.vercel.app Vercel Production에만. 로컬·Preview는 비워 둔다 공개
CRON_SECRET 매일 1회 prod DB를 깨우는 예약 작업(/api/keepalive)의 열쇠. 없어도 동작한다 아무 긴 무작위 문자열(직접 만든다) Vercel Production에만(선택) 비밀
DATABASE_URL DB 직접 연결 문자열 — scripts/db-history.ts 같은 도구 전용. 앱은 쓰지 않는다 프로젝트 [Connect] → Direct connection. [YOUR-PASSWORD]는 DB 비밀번호(모르면 Project Settings → Database → Reset database password) 로컬 .env.local(선택, dev 것만) 비밀
Google Client ID / Secret 「Google로 계속하기」의 열쇠 Google Cloud Console → Credentials → OAuth 2.0 클라이언트 코드·.env에는 없다. Supabase 대시보드 Authentication → Sign In / Providers → Google에 넣는다 Secret은 비밀

💡 Supabase [Connect] 화면은 키 이름을 NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY로 보여 줄 수 있다. 값만 가져오고 이름은 우리 것(NEXT_PUBLIC_SUPABASE_ANON_KEY)으로 쓴다. 이름이 다르면 앱이 키를 못 찾는다.

#3.2 Node.js 설치

왜 — Next.js 앱을 실행·빌드하는 엔진. npm도 함께 깔린다.

어떤 버전? — LTS(장기 지원판)를 깐다. 가장 안전한 것은 Vercel이 쓰는 버전과 같은 큰 번호다.

  • Vercel 쓰는 버전 확인: Vercel → 프로젝트 baselineplay → Settings → Build and Deployment → Node.js Version

할 일

winget install OpenJS.NodeJS.LTS

Mac: https://nodejs.org 에서 LTS 버튼의 .pkg를 받아 설치한다.

특정 버전(예: 24)이 필요하면 https://nodejs.org/en/download 에서 버전을 골라 받는다.

확인 (창을 새로 열고)

node -v
npm -v

→ v26.x.x(또는 v24.x.x)와 11.x.x 같은 숫자가 나오면 성공.

#3.4 코드 받기 (git clone)

왜 — GitHub의 코드를 내 PC로 복사한다.

어디에? — Windows는 C:\ttd, Mac은 ~/ttd(홈 폴더 아래)를 권장한다. 경로가 같으면 Claude의 메모리 폴더 이름도 같아진다(§3.10).

Windows (PowerShell):

cd C:\
git clone https://github.com/pangnima/Tennis-NTRP.git ttd
cd C:\ttd
git checkout dev

Mac (터미널):

cd ~
git clone https://github.com/pangnima/Tennis-NTRP.git ttd
cd ~/ttd
git checkout dev
  • 저장소가 비공개라 처음 clone(또는 첫 push) 때 브라우저 창이 떠서 GitHub 로그인을 물어본다(Git Credential Manager). 로그인하고 [Authorize]를 누르면 이 PC가 기억한다.
  • git checkout dev — 작업 브랜치로 옮긴다. 평소에는 항상 dev에 있어야 한다.

확인

git branch --show-current

→ dev

#3.6 .env.local 만들기

왜 — 앱이 어느 DB(dev)에 어떤 키로 붙을지 알려 준다. git에 없으므로 PC마다 만든다. 로컬은 언제나 dev 값만 넣는다(실수로 실서비스 데이터를 건드리지 않게).

할 일

  1. 견본 파일을 복사한다.

    Windows (PowerShell):

    Copy-Item .env.example .env.local

    Mac (터미널):

    cp .env.example .env.local

  2. .env.local을 편집기로 연다(VS Code: code .env.local / Windows 메모장: notepad .env.local / Mac: open -e .env.local).

  3. Supabase 대시보드에서 **dev 프로젝트(Tennis-NTRP-dev)**를 열고 §2 표대로 세 줄을 채운다.

    NEXT_PUBLIC_SUPABASE_URL=https://xiwwbgltkbvxdzxxxoba.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=sb_publishable_…(대시보드에서 복사)
SUPABASE_SERVICE_ROLE_KEY=…(대시보드에서 복사)

    NEXT_PUBLIC_SITE_URL은 비워 둔다. 나머지(#으로 시작하는 줄)는 그대로 둔다.

  4. 저장한다. = 앞뒤에 공백이나 따옴표를 넣지 않는다.

비밀번호 관리자에 예전 PC의 .env.local 값을 보관해 두었다면 그대로 붙여 넣으면 된다.

npm run dev

→ Local: http://localhost:3000 이 나오면 브라우저로 연다.

#4. 매일 개발하는 흐름

왜 — 이 순서를 지키면 실서비스는 절대 건드리지 않고 안전하게 작업이 쌓인다.

① 최신 받기 → ② 고치기 → ③ 확인 4종 → ④ 커밋 → ⑤ push → ⑥ 미리보기 확인

💬 Claude에게 맡기기: 「○○ 기능 고쳐줘」 → 끝나면 「확인하고 dev에 커밋·push해줘」. Claude는 CLAUDE.md 규칙대로 확인 명령을 돌리고 dev에만 커밋한다.

직접 하기

  1. 시작 전 — 내가 dev에 있는지, 최신인지:
    git checkout dev
git pull
  2. 코드를 고치고 npm run dev로 화면을 본다.
  3. §3.8 확인 명령 넷.
  4. 커밋 — 무엇을 바꿨는지 한 줄로:
    git add -A
git commit -m "✨ feat: 매칭 목록에 정렬 추가"
    메시지 앞머리는 관례(feat 기능 · fix 버그 · docs 문서 · refactor 정리).
  5. 올리기:
    git push origin dev
  6. 미리보기 확인 — Vercel → baselineplay → Deployments 맨 위 줄(Branch dev, 환경 Preview)이 Building → Ready가 되면 그 줄을 눌러 [Visit]. 미리보기는 dev DB라 테스트 계정으로 로그인해 본다.

    미리보기에서는 구글 로그인이 안 될 수 있다(미리보기 주소가 Supabase 허용 목록에 없어서 — 정상). 아이디 로그인으로 본다.

왜 main에서 작업하지 않나 — main에 push하는 순간 실서비스가 바뀐다. 실수 한 번이 사용자에게 바로 보인다. 그래서 main은 §6의 릴리스 때만 움직인다.

#5. DB 바꾸기(마이그레이션)

왜 — 테이블·컬럼·함수(RPC)·권한을 바꾸는 일. DB는 코드처럼 「덮어쓰기」가 안 되므로 바꾸는 SQL을 파일로 남기고, 그 파일을 차례로 적용한다.

말 뜻
마이그레이션 파일 supabase/migrations/0113_무엇.sql — 바꾸는 SQL. 번호가 순서다
적용 기록 각 DB 안의 supabase_migrations.schema_migrations 표. 「어디까지 적용했나」
재현 정본 supabase/history/ — dev 적용 기록의 사본. 새 DB를 처음부터 만들 때 쓴다

순서는 언제나 dev 먼저. prod에는 §6 릴리스 때 같은 파일을 적용한다.

💬 Claude에게 맡기기(권장): 「○○ 하려면 DB를 어떻게 바꿔야 해? 마이그레이션 만들어서 dev에 적용해줘」 Claude가 하는 일: 파일 작성 → dev에서 롤백 스모크(적용해 보고 결과만 확인한 뒤 되돌림) → dev 적용 → supabase/history·src/types/supabase.ts 갱신 → 앱 코드 수정 → 확인 4종 → dev 커밋. prod는 건드리지 않는다.

직접 하기 (Claude 없이 — 실수하기 쉬우니 가능하면 위 방법)

  1. supabase/migrations/에 다음 번호로 파일을 만든다(예: 0113_add_match_level.sql).
  2. Supabase 대시보드 → dev 프로젝트 → SQL Editor → [New query] → 파일 내용을 붙여 넣고 [Run]. 에러가 없어야 한다.
  3. 적용 기록 남기기 — 같은 SQL Editor에서 새 쿼리로 아래를 실행한다. $mig$와 $mig$ 사이에 2번에서 실행한 파일 내용을 그대로 한 번 더 붙인다.
    insert into supabase_migrations.schema_migrations (version, name, statements)
values (
    to_char(now() at time zone 'utc', 'YYYYMMDDHH24MISS'),
    '0113_add_match_level',
    array[$mig$
-- 여기에 파일 내용 전체
$mig$]
);

    빠뜨리면 「어디까지 적용했나」가 어긋나 다음 릴리스 때 prod에 무엇을 적용할지 헷갈린다.

  4. supabase/history/에 같은 내용을 <위 version>_<name>.sql로 저장한다(앞의 파일들 머리 두 줄 모양을 따른다).
  5. 타입 갱신(src/types/supabase.ts)은 Claude에게 「dev 기준으로 supabase 타입 다시 만들어줘」가 가장 쉽다.
  6. 확인 4종 → dev 커밋·push.

하지 말 것

  • prod SQL Editor에서 데이터를 직접 고치기(INSERT/UPDATE/DELETE). 실사용자 데이터다.
  • 파일 없이 SQL Editor에서만 구조를 바꾸기 — 기록이 없으면 prod에 재현되지 않는다.

#6.7 문제가 생기면 — 되돌리기

앱 되돌리기(Instant Rollback) — Vercel → Deployments → 이전 Production 줄의 ⋯ → Instant Rollback. 몇 초 만에 예전 버전으로 돌아간다(다시 빌드하지 않음).

  • ⚠ 무료(Hobby) 플랜은 바로 직전 Production으로만 되돌릴 수 있다.
  • ⚠ 되돌린 뒤에는 main에 push해도 자동으로 실서비스에 반영되지 않는다. 고친 뒤에는 프로젝트 첫 화면의 Production 카드에서 Undo Rollback을 누르거나, 새 배포 줄의 ⋯ → Promote to Production을 해야 다시 자동이 된다.
  • ⚠ DB는 되돌아가지 않는다. 앱만 옛것이 된다. 그래서 6.2의 순서가 중요하다(DB를 「더하기만」 했다면 옛 앱도 그대로 돈다).

환경변수 문제였다면 — 고치고 해당 배포 줄 ⋯ → Redeploy(§7.1 참고).

#7.1 Vercel — 프로젝트 baselineplay

Settings → Environment Variables. 변수 하나에 환경(Production / Preview / Development)을 체크해 저장한다. 같은 이름을 환경별로 따로 두 번 만든다(값이 다르니까).

변수 Production (= prod 값) Preview (= dev 값) Development
NEXT_PUBLIC_SUPABASE_URL ✅ prod URL ✅ dev URL 체크 안 해도 됨(로컬은 .env.local)
NEXT_PUBLIC_SUPABASE_ANON_KEY ✅ prod publishable ✅ dev publishable 〃
SUPABASE_SERVICE_ROLE_KEY ✅ prod 키 ✅ dev 키 〃
NEXT_PUBLIC_SITE_URL ✅ https://baselineplay.vercel.app 비움 —
CRON_SECRET (선택) — —

⚠ 환경변수를 추가·수정·삭제해도 이미 떠 있는 배포는 바뀌지 않는다. Deployments → 해당 환경의 최신 줄 ⋯ → Redeploy해야 반영된다. 특히 NEXT_PUBLIC_…는 빌드 때 코드에 박히므로 반드시 다시 빌드해야 한다.

그 밖에:

  • Production 브랜치 = main (Settings → Environments → Production의 Branch Tracking, 예전 화면에서는 Settings → Git). 다른 브랜치(dev) push는 Preview가 된다.
  • Cron(코드 vercel.json): 매일 /api/keepalive를 불러 prod DB가 7일 무활동으로 멈추지 않게 한다. Vercel → 프로젝트 → Settings → Cron Jobs에서 실행 기록을 볼 수 있다.

#8. 문제 해결

증상 원인 해결
실서비스 모든 페이지 500, 응답에 MIDDLEWARE_INVOCATION_FAILED Vercel Production에 NEXT_PUBLIC_SUPABASE_URL·_ANON_KEY가 없다 §7.1대로 넣고 Redeploy. 급하면 먼저 Instant Rollback(§6.7)
환경변수를 바꿨는데 그대로다 이미 떠 있는 배포는 안 바뀐다 해당 환경 최신 배포 ⋯ → Redeploy
로컬은 되는데 Vercel 빌드만 Error ① 환경변수 누락 ② 로컬에서 npm run build를 안 돌렸다 ③ 대소문자만 다른 파일 이름(Windows는 구분 안 함, Vercel은 구분함) Build Logs의 빨간 줄 확인 → ①은 §7.1, ②는 §3.8, ③은 파일 이름 맞추기
git push 때 Authentication failed / Invalid username or token GitHub 로그인이 만료됐다 한 번 더 push(브라우저 로그인 창이 뜬다). 안 되면 Windows: 「자격 증명 관리자」 → Windows 자격 증명 → git:https://github.com 삭제 후 다시 push
git push가 rejected (fetch first) GitHub에 내 PC에 없는 커밋이 있다(다른 PC에서 올림) git pull 후 다시 push
실수로 main에서 커밋했다(push 전) — 멈추고 Claude에게 「main에 실수로 커밋했어, dev로 옮겨줘」. 직접이면(커밋이 하나일 때) 차례로: git checkout dev → git cherry-pick main(그 커밋을 dev에 복사) → git checkout main → git reset --hard origin/main(main을 GitHub 상태로) → git checkout dev. 이미 push했다면 손대지 말고 Claude에게
구글 로그인 뒤 redirect_uri_mismatch Google 콘솔의 리디렉션 URI가 Supabase 주소와 다르다 §7.3 표와 대조
구글 로그인 뒤 Vercel 404 DEPLOYMENT_NOT_FOUND 또는 엉뚱한 곳 Supabase Redirect URLs에 우리 주소가 없어 Site URL(옛 주소)로 갔다 §7.2 Site URL·Redirect URLs 확인
Supabase 대시보드에 「Project paused」, 로그인이 안 됨 무료 플랜은 7일 무활동이면 정지된다(prod는 매일 cron이 막는다, dev는 안 막힘) 대시보드에서 Restore project(몇 분)
npm run dev 때 Port 3000 is in use 다른 창에서 이미 켜져 있다 그 창에서 Ctrl + C. 못 찾으면 PC 재시작
npm install에서 빨간 ERR! / Unsupported engine Node 버전이 너무 낮거나 설치가 꼬였다 node -v 확인 → §3.2 LTS 재설치 → node_modules 폴더 삭제 후 npm install
로컬 화면에 「NEXT_PUBLIC_SUPABASE_URL이(가) 설정되어 있지 않습니다」 .env.local이 없거나 이름이 틀렸다 §3.6. 파일 이름이 .env.local.txt가 되지 않았는지(Windows 메모장 주의)
랭킹·레이팅이 기록해도 안 바뀐다 SUPABASE_SERVICE_ROLE_KEY가 없다(또는 폐지된 Legacy 키) §2 — 해당 환경에 넣고 Redeploy. Legacy 폐지 뒤에는 sb_secret_…로 교체
claude 명령을 못 찾는다 설치 뒤 창을 새로 열지 않았다 PowerShell·터미널을 닫고 다시 연다. 그래도 안 되면 claude doctor

#9. 용어집

용어 한 줄 뜻
저장소(repository) 코드와 그 변경 기록 전체. GitHub의 pangnima/Tennis-NTRP
브랜치(branch) 같은 저장소 안의 갈래. dev = 작업용, main = 실서비스용
커밋(commit) 변경을 한 묶음으로 기록한 것(저장 시점)
push / pull 내 PC → GitHub로 올리기 / GitHub → 내 PC로 받기
merge 한 브랜치의 커밋을 다른 브랜치에 합치기(dev → main)
Pull Request(PR) GitHub 웹에서 「이 브랜치를 저기에 합쳐도 될까」를 화면으로 보여 주고 합치는 기능
빌드(build) 코드를 실제로 돌릴 수 있는 결과물로 바꾸는 과정(npm run build)
배포(deploy) 빌드 결과를 인터넷에 올리는 것. Vercel이 push를 보고 자동으로 한다
Preview / Production Vercel의 미리보기 배포(dev, dev DB) / 실서비스 배포(main, prod DB)
환경변수 코드 밖에서 넣어 주는 설정값. 환경마다 다른 값을 넣는다
NEXT_PUBLIC_ 「브라우저까지 가도 되는 공개 값」 이름표. 빌드 때 코드에 박힌다
마이그레이션 DB 구조를 바꾸는 SQL 파일과 그 적용
RLS DB 행 단위 권한 규칙 — 공개 키로 접속해도 「내 것만 보이게」 막는 장치
MCP Claude가 외부 도구(Supabase·브라우저 등)를 쓰게 해 주는 연결
Instant Rollback Vercel에서 실서비스를 직전 배포로 즉시 되돌리기(DB는 그대로)
